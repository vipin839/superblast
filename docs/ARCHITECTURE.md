# BLASTHub — architecture

Last verified against the code on 10 September 2026.

## Request path

```
browser
  └─ Firebase Auth (Google) issues an ID token
      └─ apiFetch() attaches: Authorization: Bearer <token>
          └─ Firebase Hosting (superblast.app, A 199.36.158.100)
              └─ rewrite ** -> Cloud Run service "blasthub" (us-central1)
                  └─ Next.js 16.3.x standalone server (node server.js, port 8080)
                      ├─ requireAuth()   verifies the token with Firebase Admin
                      ├─ assertOwner()   compares job.uid to the verified uid
                      ├─ blastn          native NCBI BLAST+ 2.17.0, spawn(), no shell
                      ├─ Firestore       job metadata and ownership
                      └─ Cloud Storage   result payloads (shared across instances)
```

## Authentication and authorization

Every `/api/*` route calls `requireAuth(request)` before anything else.

The server derives the caller's uid **only** from a verified Firebase ID
token. No route reads a uid from a query string or a request body. `POST
/api/jobs` strips `uid` and `ownerUid` from the payload before writing.

`assertOwner(job, uid)` returns **404** when a job exists but belongs to
someone else — identical to the response for a job that does not exist — so
responses cannot be used to enumerate job IDs.

| Condition | Status |
|---|---|
| No or malformed `Authorization` header | 401 |
| Token expired / revoked / user disabled | 401 (distinct messages) |
| Authenticated, job belongs to another user | 404 |
| Authenticated, job does not exist | 404 |
| Over the per-user rate limit | 429 |

`GET /api/blast/test` is additionally gated to `ADMIN_EMAILS`. If that
variable is empty the endpoint returns 404 and does not exist in practice.

## Identifiers

| Kind | Format | Generated by |
|---|---|---|
| Job ID | `job_` + 32 hex (128 bits CSPRNG) | `src/lib/ids.js`, mirrored for the browser in `src/lib/apiClient.js` |
| BLAST request ID (RID) | 16 lowercase hex (64 bits CSPRNG) | `src/lib/ids.js` `newRid()` |

RIDs become filename components, so `RID_PATTERN` (`/^[a-f0-9]{16}$/`) is
applied by `assertRid()` before any path is constructed. Generation and
validation live in the same module so they cannot drift.

One RID is minted per uploaded file in the submit route and used everywhere:
the temp query file, the temp output file, the stored result object, and the
value returned to the client. (Previously the submit route and the engine each
generated their own, so they referred to different searches.)

## Result storage

Results live in Cloud Storage, not on the container filesystem:

```
gs://$BLAST_RESULTS_BUCKET/results/<uid>/<rid>.json     completed result
gs://$BLAST_RESULTS_BUCKET/results/<uid>/<rid>.error    failure marker
```

Any instance can serve any poll. The uid prefix means a leaked RID alone does
not grant access to another user's results.

`BLAST_RESULTS_BUCKET` is **required in production**. If it is unset,
`resultStore.js` throws on the first write rather than silently falling back
to instance-local files. Development without a bucket uses the temp directory
and `storageMode()` reports `sharedAcrossInstances: false`.

The container filesystem is still used for the two transient files BLAST+
needs (`query_<rid>.fasta`, `out_<rid>.json`), which are deleted as soon as
the search finishes.

## Job cancellation — and its honest limit

`src/lib/nativeBlast.js` keeps a registry of live child processes keyed by RID.
`POST /api/blast/cancel` authenticates, then:

- If the search is running **on the instance handling the cancel request**,
  the process receives SIGTERM, escalating to SIGKILL after 5 s. It genuinely dies.
- If it is running on a **different** instance, the registry cannot reach it.
  The search is marked cancelled in shared storage so the UI stops polling,
  and the response says exactly that in its `note` field. The orphaned process
  still exits at its own timeout (see `DB_TIMEOUTS`).

The UI surfaces that `note` verbatim. Nothing reports "terminated" for a
process that is still running.

Making cancellation reliable across instances would need a shared control
channel (Pub/Sub fan-out to every instance, or moving BLAST execution to a
worker pool with a job queue). That is a larger change than this pass.

## Rate limiting — and its honest limit

`src/lib/apiAuth.js` holds per-user counters **in one instance's memory**.

| Bucket | Limit |
|---|---|
| `submit` | 20 per hour |
| `analyze` (Gemini) | 15 per hour |
| `read` (polling, listing) | 600 per hour |
| concurrent searches | 3 |

With `max-instances 10`, a caller spreading requests across instances can
reach up to limit × instances. These are a cost guard against runaway clients
and accidental polling loops, **not** a security boundary. A global limit
needs Firestore or Redis.

## AI interpretation

`POST /api/blast/analyze` takes only a `jobId`. The server verifies ownership,
loads the results **it stored** from Cloud Storage, and builds the prompt
itself. No caller-supplied text reaches the model, so the endpoint cannot be
used as a general Gemini proxy.

- Model: `gemini-2.5-pro` (stable ID, not a preview alias)
- Key: `GEMINI_API_KEY`, server-side only, sent as the `x-goog-api-key`
  **header** — never a URL parameter
- The prompt fences measurements inside `=== OBSERVED BLAST DATA ===` and
  instructs the model to treat that block as data, never as instructions

When the key is absent or the API fails, the response carries
`source: "local-summary"`, `model: null`, a `status` of `unavailable` or
`failed`, and a `reason`. The UI badge then reads "Local summary", never
"Gemini". A deterministic statistical summary is shown in its place and is
labelled as containing no AI inference.

## Build and deployment

The image is split so that deploys stop paying for database indexing:

| Image | Contents | Rebuild when |
|---|---|---|
| `blasthub-base:blast2.17.0-db2` | Debian + BLAST+ 2.17.0 + all reference databases | the engine version or a database definition changes |
| `blasthub:latest` | `FROM blasthub-base`, plus the Next.js standalone build | every code change |

Application builds no longer download BLAST+ or run `makeblastdb`. Cache
invalidation is explicit: bump `BASE_TAG` in the `Dockerfile`.

See [DEPLOYMENT.md](DEPLOYMENT.md) and [DATABASES.md](DATABASES.md).

## Cloud Run configuration

| Setting | Value | Why |
|---|---|---|
| Region | us-central1 | matches the Firebase Hosting rewrite |
| Memory | 4 GiB | BLAST+ working set plus the RAM-backed writable filesystem |
| CPU | 2 | `-num_threads 2` |
| CPU throttling | off | BLAST batches continue after the HTTP response returns |
| min-instances | 1 | avoids a cold start that would exceed the poll interval |
| max-instances | 10 | |
| Concurrency | 80 | |
| Request timeout | 300 s | submit returns immediately; searches run in the background |

`min-instances: 1` is deliberate and must not be set to 0: submissions are
processed after the response is sent, and a scale-to-zero would kill them.

## Known limitations

1. Cancellation is best-effort across instances (above).
2. Rate limits are per-instance (above).
3. The human GRCh38 database is not provisioned; the option is disabled with a
   stated reason rather than shown as available.
4. The service runs as the default compute service account, which is broadly
   privileged. A dedicated service account with only Firestore, Storage and
   log-write permissions would be better.
5. The results bucket is in us-east4 while the service runs in us-central1 —
   cross-region reads on every poll. Functional, but a same-region bucket
   would be faster and cheaper.
